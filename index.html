A NOTE FROM THE DEVELOPER

Why I am building h/monhook.

I started h/monhook with a simple frustration: a trader can carefully choose a route, set slippage and sign a transaction, yet the promise they saw in the interface is still separate from the result that finally settles on-chain. Most tools explain the trade before it happens or analyse it after it happens. I want the promise itself to become executable.

That is why the hook in h/monhook does not belong to one pool. It belongs to one transaction. The user signs the outcome they are willing to accept—how much may leave, how much must arrive, which route may execute, when the intent expires, and which extra policy must pass. h/monhook Guard surrounds the route, measures what actually changed, and lets Solana commit the transaction only when those conditions hold.

The same question starts before a trade: what did a developer promise, and can a buyer verify it? I want same-name launches to be compared by Mint, developer, locked supply and option terms instead of a familiar ticker alone. After settlement, users should also have a choice of private transfer where it is compatible with that public evidence. Those issuer and privacy layers are designs I am working toward; today's supported settlement path uses the h/monhook Guard on mainnet.

I do not want h/monhook to be another dashboard wearing protocol language. I am building the program, SDK, manifest formats and product surfaces together so the idea can be used by token creators, wallets, routers and ordinary traders. I am publishing the work as it develops because the mechanism should be inspectable, testable and improved in public.

— The h/monhook developer
Building intent-bound settlement on Solana.

IN PLAIN LANGUAGE

h/monhook turns “I expect this trade” into “only settle if this is true.”

Today, a trading interface usually shows an estimate, slippage setting and route before the wallet opens. The user signs the assembled transaction, but the promise they understood still lives mainly in interface text. If several programs, pools or token extensions affect the route, explaining the quote and enforcing the final result become two different jobs.

h/monhook joins those jobs. The wallet encodes the user’s maximum spend, minimum receive amount, permitted route and expiry into one intent. h/monhook Guard runs the route and measures the real balance changes before Solana commits the transaction. The user is not asking h/monhook to find liquidity; they are asking it to reject any result outside the boundary they signed.

A SIMPLE EXAMPLE

A user authorizes spending no more than 1 SOL and receiving no fewer than 950,000 token units. Receiving 970,000 after spending 0.98 SOL passes. Receiving 940,000—or spending 1.01 SOL—fails the signed condition and the transaction reverts.

WHY THIS WORKS ON SOLANA / OFFICIAL CAPABILITIES

The runtime already provides the execution model h/monhook needs.

A Solana program can call another program through Cross-Program Invocation. The invoked route shares the same transaction’s remaining compute budget and receives only the signer and writable account privileges that the caller explicitly passes. h/monhook can therefore place h/monhook Guard around a router or market instruction, run that route through CPI, reload the affected token accounts, and reject settlement when a signed postcondition is false. Because the instructions belong to one atomic transaction, a failed postcondition causes the transaction path to fail rather than leaving a partially accepted result.

Token-2022’s Transfer Hook solves a different problem. It attaches custom logic to a particular Mint and runs that logic on every transfer involving that token. h/monhook moves the hook boundary up to the complete transaction intent: one user-selected trade can cross a router, several pools and either token program, while h/monhook Guard checks the final realized input and output of the route as a whole.

THE IDEA / IN PLAIN LANGUAGE

One trade. One signed promise. One atomic result.

A pool hook controls a pool. An intent hook protects the user’s selected transaction, even when the route moves through several programs.

Think of a pool hook as a rule attached to a place: whenever activity enters that pool, the pool’s rule runs. An intent hook is a rule attached to a decision: whenever this user’s specific transaction executes, the user’s rule travels with it. This is why h/monhook can protect the complete economic outcome instead of only one stop along the route.

Pool-bound hooks

  • Live inside one liquidity venue.
  • Are usually selected by the pool or asset creator.
  • See only the activity that enters that venue.
  • Cannot describe the user’s complete multi-program route.

h/monhook intent hooks

  • Travel with one user-authorized transaction.
  • Protect maximum input and minimum output.
  • Restrict route, expiry and custom policy conditions.
  • Commit with a receipt or revert the whole route.
HOW IT WORKS

Declare first. Execute second. Settle only if true.

h/monhook does not invent liquidity. It wraps the route selected by the user or interface and enforces the signed economic boundary around it.

01 / DECLARE

Set the outcome

The wallet defines max input, min output, expiry, route and optional policy data.

02 / AUTHORIZE

Sign the intent

A canonical manifest binds those constraints to the user and derives an intent identity.

03 / EXECUTE

Run the route

h/monhook Guard snapshots balances and invokes the selected programs through CPI.

04 / VERIFY

Commit or revert

Real balances are reloaded. Valid outcomes return a JRC1 receipt; invalid ones roll back.

For a trader, this means the interface is no longer asking them to trust a descriptive quote alone. The maximum spend and minimum receive values become part of the instruction data. For an integrator, it means an existing route can remain responsible for finding liquidity while h/monhook Guard remains responsible for deciding whether the realized result is acceptable.

The receipt is important for the same reason. A successful JRC1 result records the intent identity and measured balance changes, giving wallets and indexers a direct settlement artifact instead of forcing them to reconstruct the user’s original guarantee from interface text.

COMMON QUESTIONS

The boundaries are part of the product.

Is h/monhook another AMM or a Solana explorer?

No. h/monhook is a settlement wrapper and policy interface. Existing launchpads, AMMs and routers provide liquidity; h/monhook Guard enforces the user’s signed conditions around their route.

Why not attach the hook directly to every pool?

Because a user’s route may cross several programs and pools. Binding the hook to the intent gives the transaction one economic boundary from start to finish.

What happens when a condition fails?

The guard returns an error. Solana’s atomic transaction model rolls back the route, so the protected transaction does not settle partially.

Where is the official token address published?

In the official contract-address box at the top of this page, in the Markets directory and through the linked h/monhook X account. Always verify the complete Mint before interacting.

Can buyers use issuer options or private transfers now?

No. Issuer locks, options, forfeiture claims and Helius Privacy Rings integration remain outside this release. The verified h/monhook Guard is on mainnet for the supported Jupiter route; a deployed program alone does not mean every wallet or route is integrated.
