# h/monhook protocol release status

The public GitHub Pages site is still using the existing deployed Guard program. The new h/monhook programs in this branch are **development artifacts**, not deployed to Solana mainnet.

## Unified mainnet release

The owner chose to finish the product and launch its money-facing features as one release. The old Guard-only deployment script is inspection-only; its `-Deploy` switch deliberately fails. A standalone, public metadata and directory service has been deployed for non-funding integration tests; this does not activate new on-chain programs or publish the development front end. The final release still needs one plan covering both program binaries, market and privacy integrations, site configuration, authority backup, funding, and post-deployment transactions. No mainnet release date or SOL amount is established yet.

As of 2026-11-24, the two current SBF binaries are 33,064 and 148,080 bytes. A mainnet RPC rent query returned 0.16884396 and 0.75312524 SOL for their respective ProgramData accounts, or 0.92196920 SOL together. Program accounts, temporary deployment buffers, transaction fees and user-created accounts are additional; 0.5 SOL cannot cover both deployments. Recalculate from the final audited binaries before funding. CI-generated program keypairs are disposable and must never become mainnet program identities; the SBF artifact workflow now publishes only binaries and hashes.

The remaining hard gates are: (1) enforce or explicitly redesign the curve-derived strike rule in the program; the new Rust parser has unit coverage but is not yet called by series initialization; (2) choose a durable, truthful developer-sale rule, since a treasury outflow followed by a refill is not currently provable; (3) run the full launch, lock, purchase, exercise/default, refund and buyback paths with funded public-cluster transactions and real pools; (4) obtain independent security review, prepare separately controlled deployment and upgrade authorities, verify deployed SBF hashes, and then enable the mainnet configuration. Privacy Rings is still an unimplemented integration and cannot be advertised as active.

## Verified locally

- `programs/hmonhook-guard` builds to SBF. Its own wire marker is `HMON`, and `hmonhook-sdk` builds matching instructions and receipts.
- A disposable local validator executed a Token-2022 transfer routed through the new Guard; the SDK's exact max-input rule rejected a second transfer and reverted its token movement. Run `node scripts/test-guard-local.mjs <local-guard-program-id>` after deploying the SBF program to a local validator.
- `programs/hmonhook-options` builds to SBF. The disposable local validator exercised series creation, purchase, exercise, registered-treasury default, default claim, duplicate-claim rejection, early reclaim of unsold collateral while sold lots remained exercisable, expiry, and final reclaim. It also rejected premature default, buying after the registered treasury was already breached, redirected exercise payout, purchase after the sale deadline, and unauthorized collateral reclaim; the premium deposit was checked against the series' SOL balance. The vault now rejects a preapproved token delegate and a nonempty balance before opening; Rust unit tests check both delegate fields. Run `node scripts/test-options-local.mjs <local-options-program-id>` after deploying the SBF program to a local validator.
- The options program now requires the collateral source and monitored issuer treasury to be the same token account. It checks the promised treasury floor against the balance after collateral is deposited and verifies that exact balance after transfer. A fresh local-validator run rejected a distinct unmonitored source while the normal purchase, exercise, default claim and reclaim paths passed. This still observes only one registered account; a separate evidence/indexing layer is necessary before claiming to detect sales from every developer-controlled wallet.
- The development series and position account tags are `HMONOPT2` and `HMONPOS2`. Premiums now enter a separate system-owned buyback PDA with a rent reserve paid by the issuer. A buyer-authorized post-expiry instruction refunds unspent premiums pro rata and rejects duplicate claims. Once no premium remains, anyone can return the PDA's rent to the fixed issuer address. The original option lifecycle and a 200-lamport refund for two lots passed again on a locally deployed SBF.
- The options program now has a constrained CPI route to Pump `buy_exact_quote_in_v3`. It checks sellout, expiry, the official Pump program and account layout, Mint, fee recipient, destination vault, spendable premium, token output and a maximum price of twice the series strike. A keeper provides temporary SOL for Pump account rent; the program returns unused top-up without returning premium principal. A local-validator Pump test double bought 1,000,000 base units with 2,000 premium lamports and refunded the remaining 3,000 lamports after expiry; substituted-vault, too-low output and excess-spend transactions failed without reducing the premium balance. A second test loaded Pump's deployed mainnet SBF and cloned its global/fee accounts: it created a Pump coin, locked 2% of supply, sold the options, and bought 310,858,132,043 base units with 10,000,000 premium lamports; the PDA balance fell by exactly that amount. This verifies the local route against the actual Pump binary, but not the migrated PumpSwap path or funded devnet. `npm audit` reported 15 upstream/transitive dependency advisories for the current pinned Solana/Pump stack; its suggested major-version changes would break the integration, so dependency impact needs a targeted review rather than an automatic forced rewrite.
- CI checks both Rust programs, both SDKs, and the options client. Local-validator tests need a running Solana validator and remain manual.

## Release blockers

1. A dedicated management wallet was generated on the project owner's Windows computer. Its public address is `DyjJ2cxfL3oYCnazLHB7zpe4sd4mSnQuCbqV5sDGrgmG`. Its private key is outside the repository under that Windows user's application data, with access limited to that user. It has **0 SOL on mainnet** as checked on 2026-11-24, so it cannot currently pay to deploy. The owner still needs an offline recovery backup before any production authority is entrusted to it. The local-validator payer is separate and must never become the production authority.
2. Stable public addresses were reserved for the new Guard (`Be7RvxKNFa35ER8DSmPoBq6AssMMoJsMU4fBso1E2ELQ`) and options (`Cz1jDZv12iXcK5JTY3s4wFX6HH8Y48xDeRxPWDgqshNQ`) programs; their private program keypair files are stored outside the repository. These addresses currently identify local-validator deployments only, not mainnet programs.
3. The development options program has a locally tested Pump-curve buyback route using the deployed Pump SBF. Its canonical SOL-quoted PumpSwap V2 route passed both a test double and a run against PumpSwap's actual deployed SBF: a sold-out series spent exactly 2,000 premium lamports, bought 3,304,115 base units with the actual binary, rejected substituted vaults and unsafe amounts, refunded unused premiums after expiry, and recovered the wrapped-SOL ATA rent. The actual-binary run used a synthetic canonical pool and cloned mainnet config/fee accounts, not a pool created by migration or a funded public cluster. The permanence of the acquired-token vault also depends on final upgrade-authority controls. See `docs/OPTIONS_PREMIUM_EXECUTION.md` for the release invariants. Do not deploy it with real user funds.
4. A funded devnet deployment, adversarial runtime tests, and independent security review are needed before mainnet collateral or options are accepted. A fresh disposable devnet payer received 0 SOL: the public RPC `requestAirdrop` returned HTTP 410, the Solana CLI airdrop was rate-limited, and the official proof-of-work faucet could not complete through the available devnet RPC. The dedicated faucet's agent guidance recommends those two programmatic methods; neither has funded this test yet. The current Guard and options SBF binaries are 33,064 and 148,080 bytes. Mainnet rent queries for their 45-byte ProgramData prefixes returned 0.16884396 and 0.75312524 SOL respectively, or 0.92196920 SOL together before program accounts, temporary deployment buffers, transactions, user positions and operating reserves. A 0.5 SOL production wallet would therefore be insufficient even for these two ProgramData accounts at the current binary sizes. Recalculate exact costs and network state before any mainnet funding request.
5. The new R2 launch directory verifies submitted Pump `create_v2` transactions and indexes those launches by exact normalized name, but it has not passed a real signed launch registration yet. It is narrower than a global index of every Solana token with the same name. GitHub Pages cannot write that index by itself.
6. Helius Privacy Rings integration requires a project Helius account, API access and production configuration. No privacy claim should be shown as live until a real transaction is verified.
7. Wallet launch and Jupiter paths need end-to-end signed tests with the eventual project-owned Guard program and production RPC.

## Launch front-end state

- The website's coin creation action builds Pump `create_v2` for Solana mainnet and requires a wallet signature. It does **not** call the new Guard or create an issuer option position. The current live GitHub Pages branch still requires an existing public metadata URI; the development branch now points to the separate upload service.
- The launch client now checks that the connected wallet matches the payer and rechecks the transaction signature after an RPC confirmation timeout. Unit tests cover confirmed, failed and unresolved signatures. This is not a funded mainnet launch test.
- The development launch page now invalidates a compiled plan if the connected wallet changes before submission; the new wallet must compile its own plan before signing. The upload instructions now describe the deployed development metadata service accurately. This still has not passed a funded, signed end-to-end launch.
- If a wallet submitted a transaction but RPC confirmation is unresolved, the development front end now preserves the signature and Mint, labels the local receipt `CONFIRMATION PENDING`, avoids counting it as a verified launch, and retries directory verification from the market page. It does not invite another launch attempt. The form records an immutable snapshot of the signed name, symbol and metadata even if inputs change during wallet approval. A confirmed transaction is called a verified Pump creation only after the directory checks its on-chain instruction.
- `scripts/launch-mainnet-test.mjs` now uses h/monhook test metadata and an explicit `HMONHOOK_KEYPAIR_PATH`; it only simulates and rejects `--send` while the unified release is incomplete.
- After a confirmed launch, the website generates a shareable `markets/?mint=<address>` link. The current live branch still saves its automatic launch receipt only in the creator's browser. The development branch additionally submits it to the independent directory for on-chain verification and cross-device display; no real signed launch has exercised that path yet.
- A separate public Sites Worker/R2 service now exists under `services/launch-api`. Its mocked end-to-end test covers upload, public image/JSON retrieval, verified Pump launch registration and exact-name search. The Sites project `appgprj_6b04a10d4dbc8191979f45f72651b37a` is deployed at `https://hmonhook-launch-api.zaunmanx.chatgpt.site`. A real HTTP upload, public JSON and PNG fetch, empty directory read and CORS preflight passed on 2026-11-24. The development branch now points its upload and registry configs to this endpoint. These changes have not been published on the existing GitHub Pages main branch. No funded Pump launch or cross-device registration test has yet been run, and per-IP limits are not a complete abuse defense.
- A production RPC read exposed Solana v1 transactions. The Sites service was updated to request `maxSupportedTransactionVersion: 1` and to try the official Solana public RPC if its primary provider fails. Site version 2 deployed successfully, then `/health` and the directory returned 200. A real v1 transaction submitted with deliberately mismatched Mint and creator was rejected with HTTP 422; the directory stayed empty. The alternate Supabase function now requests v1 as well. This does not substitute for a real signed launch registration.
- Site version 3 adds artwork and description to verified directory rows when the launched Mint points to immutable metadata hosted by this service and its name and symbol match the Pump creation. The market page now displays that artwork on another device without waiting for a third-party price index. Unit tests cover the upload-to-directory path; a real signed cross-device launch test is still outstanding.
- Site version 4 uses R2 conditional writes to enforce each Cloudflare client IP's daily upload and registry submission cap under concurrent requests. A 30-request concurrent test stayed at or below the 20-upload limit; a live invalid upload returned HTTP 400 after passing the limiter. Distributed-client abuse and production traffic monitoring still need handling.
- The development market page now describes the verified cross-device directory accurately. An unused Joltwork test-token metadata file was removed from the public bundle, and the empty static registry now carries the h/monhook format name. Legacy Jolt Guard source remains available with explicit lineage disclosure.
- The development Source Code page now opens the new h/monhook Guard first and lists the options program and new SDK separately from the deployed legacy Guard. The local site bundle includes every file linked by its source browser; a local HTTP check returned 200 for both new Rust programs, the new SDK and the legacy Guard. This is source visibility, not a mainnet deployment.
- The installed Pump SDK's `create_v2` instruction currently selects Token-2022, matching the new options program's supported token program. The browser launch client and simulation script now reject a changed SDK account layout or token program before a wallet is asked to sign. A regression test exercises the installed SDK instruction without sending funds.
- The launch client and mainnet simulation now share a strict `create_v2` validator: it checks the expected 16 account addresses and signer flags, instruction discriminator, name, symbol, URI, creator, and disabled optional launch flags before signing. The source browser includes this validator and launch-confirmation code. This is a transaction construction check; it is not a funded launch or proof that the entire issuer protection flow is live.
- Site version 5 repairs a partial verified-launch directory write on the next valid registration attempt. Its storage-failure regression test first interrupts the time index, then retries the same confirmed transaction and checks both the recent list and exact-name search. The deployed service returned HTTP 200 for `/health` and an empty `/launch-registry` after publication. No real signed launch registration has yet exercised this recovery on production storage.
- The older Supabase migration and Edge Functions remain as an unused alternative. The deployed Sites/R2 service avoids needing a Supabase project for this launch path, but still needs a real signed launch registration, a production RPC reliability check and stronger abuse controls before the main branch uses it. See `supabase/README.md` for the older design.

The current website must keep unsupported actions clearly labeled until these gates are met. Do not point it to the disposable local program IDs in this branch.
